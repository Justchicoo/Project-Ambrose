# 12.22 spike: same-connection zone transfer (MSG_ZONETRANSFER)

## Question (WLD-21)

Can the retail client change zones on the same connection, without the
disconnect plus MSG_SERVERTRANSFER plus re-attach round trip? If so,
adopt it: it is faster than a reconnect.

## What the retail client declares

From contrib/findings/protocol/service-005-game.json, decoded from the
client's own message table:

MSG_ZONETRANSFER (order 250), server to client:

- ZoneName (STR), ZoneID (GID), Slot (INT), DynamicZoneID (UINT),
  DynamicServerProcID (UINT), ZoneCounter (UBYT), TransitionID (UINT),
  SessionID (GID), SessionSlot (INT)

MSG_UPDATEZONECOUNTER (order 243), server to client:

- ZoneCounter (UBYT)

The behavior reference (retail captures) never sends MSG_ZONETRANSFER.
Every zone change observed goes MSG_ZONETRANSFERREQUEST, then
MSG_ZONETRANSFERACK, then MSG_SERVERTRANSFER, then a reconnect, then
MSG_ATTACH, then MSG_LOGINCOMPLETE.

## What the server now does

Zone.TransferMode is a live setting, reconnect or inprocess, default
reconnect, read at each transfer so `.settings set Zone.TransferMode
inprocess` applies to the next transfer without a restart. Anything but
inprocess falls back to reconnect.

- reconnect (default): the proven path, unchanged. The client gets
  MSG_SERVERTRANSFER with a single-use key and re-attaches.
- inprocess: after the client's MSG_ZONETRANSFERACK the server moves
  the wizard to the new zone's public instance on the SAME connection,
  bumps the zone counter, sends MSG_ZONETRANSFER carrying the new
  zone's name, ZoneID, DynamicZoneID, DynamicServerProcID and
  ZoneCounter+1, then the new zone's login-complete flow: the wizard's
  object re-serialized at its arrival place with its new mobile id,
  MSG_LOGINCOMPLETE with the new zone's ids and critical objects, and
  the sight repopulated. The wizard's player state (stats, spellbook,
  backpack, equipment, quest log) is kept; only the zone changes.

MSG_UPDATEZONECOUNTER is declared for intra-cluster moves where only
the counter needs resyncing; the inprocess path carries the counter in
MSG_ZONETRANSFER itself, so the standalone message waits for a real
client to show a case that needs it.

## Expected client behavior (to verify with the real client)

1. The wizard stands in WizardCity/WC_Hub. `.settings set
   Zone.TransferMode inprocess`.
2. `.tele zone WizardCity/WC_Ravenwood`: the server sends
   MSG_ZONETRANSFERREQUEST; the client shows its loading screen and
   answers MSG_ZONETRANSFERACK.
3. The server sends MSG_ZONETRANSFER (Ravenwood, ZoneCounter+1) then
   MSG_LOGINCOMPLETE for Ravenwood, on the same connection.
4. The client loads Ravenwood with NO socket reconnect. Verify: the
   server connection log shows no new connection for the character,
   and the session id on the server side is unchanged.
5. The client's first MSG_CLIENTMOVE after arrival carries the new
   ZoneCounter; moves under the old counter keep being ignored as
   stale.

## If the client stalls

Record the observed state: the client log lines around the transfer,
which message it waited on, whether the loading screen cleared. The
default stays reconnect. Known unknowns going in:

- Whether the client wants MSG_LOGINCOMPLETE after MSG_ZONETRANSFER,
  or treats MSG_ZONETRANSFER itself as the zone-complete signal.
- What it does with SessionID/SessionSlot on an already-attached
  connection (the reconnect path leaves them zero too).
- Whether it reuses or resets its zone counter on MSG_ZONETRANSFER.
