# loginserver options

See doc/config/README.md for the file format, layers, environment variable names, and reload triggers, and doc/config/logging.md for the full logging grammar.

The Applies column says when a changed value takes effect after a configuration reload or a live edit. No option in this file needs a restart. The socket layer applies the network options through `SocketMgr::ApplySettings`; the reload triggers that call it arrive in milestone 4.15.

| Option | Type | Default | Environment variable | Applies | Meaning |
|---|---|---|---|---|---|
| `LogsDir` | string | `logs` | `AMBROSE_LOGS_DIR` | Live | Folder for log files, relative to the working directory unless absolute; created when a File appender exists |
| `BindIP` | string | `0.0.0.0` | `AMBROSE_BIND_IP` | Rebinds live like the port option | Local address the listener binds; 0.0.0.0 listens on every IPv4 address |
| `LoginServerPort` | uint16 | `12000` | `AMBROSE_LOGIN_SERVER_PORT` | Rebinds live; the new listener opens before the old one closes, and a failed bind keeps the old one | TCP port the login server listens on for clients |
| `Patch.Enabled` | bool | `0` | `AMBROSE_PATCH_ENABLED` | Live, from the next login once milestone 16.07 consumes it | 0 for development with the client launched with -P 0 (doc/PATCHING.md); 1 expects clients to patch through the patchserver |
| `ClientDir` | string | empty | `AMBROSE_CLIENT_DIR` | Live once the reload triggers of milestone 4.15 reload messages; a folder that fails to load keeps the active definitions | Your own Wizard101 install, the folder that holds `Data` and `Bin`. The message definitions load from its `Data/GameData/Root.wad`, and one that fails to load at startup stops the server. When an install is in use, clients will be served, so startup also stops, naming where `ClientDir` came from, when no type dump is in use or `LoginDatabaseInfo` or `CharacterDatabaseInfo` is empty. When the value is empty or holds no install and neither the environment nor the command line sets it, `Setup.Mode` decides at startup: `auto` uses the install with the newest revision found on this machine, `ask` offers the installs found, and `off` uses the value as it is. A chosen install is saved to `conf.d/client-data.conf` only when a type dump is in use for it; otherwise it is not used, and setup tries again on the next start. `auto` never replaces a value that names a folder without an install, which may be only unavailable for now: it uses the newest install for that run only and warns. An install found at a path that is not valid Unicode is skipped with a warning. With no install in use, client messages are logged by service and order only |
| `TypeDumpPath` | string | empty | `AMBROSE_TYPE_DUMP_PATH` | At startup, and live once 4.15's reload triggers reload it; a dump that fails to load keeps the active one | A type dump (format v2) made from your own client. Every class and property hash is checked when it loads, and one that fails to load at startup stops the server. Empty means the dump built from the install in use, `types/<revision>.json` in the Ambrose data folder (`%LOCALAPPDATA%/ProjectAmbrose` on Windows, otherwise `$XDG_DATA_HOME/project-ambrose` or `~/.local/share/project-ambrose`). In `auto` mode that dump is used when the revision and client program SHA-256 recorded in its header match the install, and otherwise `Setup.TypeExtractor` builds it first; it is never saved here. `ask` uses that dump without asking when it is current; otherwise it offers to build it when no dump found on this machine is named `<revision>.json` for the install, then offers the dumps found and saves the one chosen to `conf.d/client-data.conf`. `off` uses no dump. A value that is not a type dump is handled like an empty one, unless the environment or the command line sets it or `Setup.Mode` is `off`, and a value the command line sets empty stays empty, with no dump built or asked for. A dump found at a path that is not valid Unicode is skipped with a warning. With no dump in use, ObjectProperty data stays unreadable |
| `Setup.Mode` | string | `auto` | `AMBROSE_SETUP_MODE` | At startup | How the login server sets up its client data when `ClientDir` or `TypeDumpPath` is empty or unusable and not set by the environment or command line. `auto` never asks: in place of `ClientDir` it uses the install with the newest revision found on this machine, saving it to `conf.d/client-data.conf`, which then reloads, when `ClientDir` is empty, and in place of `TypeDumpPath` it uses or builds the type dump of the install in use. `ask` uses a current built type dump without asking, asks on an interactive terminal which install and type dump to use, or whether to build the dump, and saves the choice to the same file; without a terminal it logs what it found and the setting to add. In both modes an install is saved only when a type dump is in use for it. `off` searches for nothing and builds nothing. Any other value is reported and runs as `auto` |
| `Setup.PromptTimeout` | uint32 | `120` | `AMBROSE_SETUP_PROMPT_TIMEOUT` | At startup | Seconds each setup question in `ask` mode waits for an answer; 0 waits forever. When time runs out or a stop signal arrives, that question and every later one are skipped |
| `Setup.TypeExtractor` | string | empty | `AMBROSE_SETUP_TYPE_EXTRACTOR` | At startup | The typeextract executable that builds the type dump of the install in use; empty uses `typeextract` beside the login server's executable. A relative path is resolved against the working directory and run as that exact file, never searched for on `PATH` |
| `Setup.TypeExtractTimeout` | uint32 | `900` | `AMBROSE_SETUP_TYPE_EXTRACT_TIMEOUT` | At startup | Seconds a type dump build may run before typeextract and everything it started are ended and the build fails; 0 sets no limit. Another process waits on a running build, however long it runs, and builds at once when the process holding the build lock has ended. A stop signal ends a build or the wait for one |
| `ObjectProperty.MaxDepth` | uint32 | `64` | `AMBROSE_OBJECT_PROPERTY_MAX_DEPTH` | Live, from the next decode once 4.15's reload triggers reload configuration; out-of-range values are clamped and reported | How deeply objects inside a decoded ObjectProperty blob may nest, from 1 to 128; the ceiling keeps a decode within a thread's stack |
| `ObjectProperty.MaxObjects` | uint32 | `65536` | `AMBROSE_OBJECT_PROPERTY_MAX_OBJECTS` | Live, from the next decode once 4.15's reload triggers reload configuration; out-of-range values are clamped and reported | How many objects one decoded blob may hold, from 1 to 16777216 |
| `ObjectProperty.MaxContainerCount` | uint32 | `65536` | `AMBROSE_OBJECT_PROPERTY_MAX_CONTAINER_COUNT` | Live, from the next decode once 4.15's reload triggers reload configuration; out-of-range values are clamped and reported | How many elements one list in a decoded blob may hold, from 0 to 16777216 |
| `ObjectProperty.MaxDecodedBytes` | uint64 | `16777216` | `AMBROSE_OBJECT_PROPERTY_MAX_DECODED_BYTES` | Live, from the next decode once 4.15's reload triggers reload configuration; out-of-range values are clamped and reported | Memory one decode may build, in bytes, from 65536 to 1073741824; objects, list elements, default values and strings are charged before they are allocated |
| `ObjectProperty.MaxInflatedSize` | uint64 | `4194304` | `AMBROSE_OBJECT_PROPERTY_MAX_INFLATED_SIZE` | Live, from the next decode once 4.15's reload triggers reload configuration; out-of-range values are clamped and reported | Largest size, in bytes, an enveloped blob may declare or inflate to, from 1024 to 268435456 |
| `LoginDatabaseInfo` | string | `127.0.0.1;3306;ambrose;ambrose;ambrose_login` | `AMBROSE_LOGIN_DATABASE_INFO` | Live once 4.15's reload triggers call the database loader: a new pool opens and is validated, then replaces the old one, which drains its queued work; a failure keeps the old pool | Login database as `host;port;user;password;database[;tls[;ca file]]`, where tls is `off`, `tls` or `tls-verify` and host `.` takes a socket or pipe name in the port field. An invalid or unreachable value stops startup; an empty value, or no key at all, leaves the database closed |
| `LoginDatabase.WorkerThreads` | uint32 | `1` | `AMBROSE_LOGIN_DATABASE_WORKER_THREADS` | Live like `LoginDatabaseInfo` | Async connections, each with its own worker thread (0-64) |
| `LoginDatabase.SynchThreads` | uint32 | `1` | `AMBROSE_LOGIN_DATABASE_SYNCH_THREADS` | Live like `LoginDatabaseInfo` | Connections for blocking queries (1-64) |
| `CharacterDatabaseInfo` | string | `127.0.0.1;3306;ambrose;ambrose;ambrose_characters` | `AMBROSE_CHARACTER_DATABASE_INFO` | Live like `LoginDatabaseInfo` | Characters database the character list reads, in the connection string form above; the login and game servers share it, because a wizard is not tied to one realm |
| `CharacterDatabase.WorkerThreads` | uint32 | `1` | `AMBROSE_CHARACTER_DATABASE_WORKER_THREADS` | Like `CharacterDatabaseInfo` | Async connections, each with its own worker thread (0-64) |
| `CharacterDatabase.SynchThreads` | uint32 | `1` | `AMBROSE_CHARACTER_DATABASE_SYNCH_THREADS` | Like `CharacterDatabaseInfo` | Connections for blocking queries (1-64) |
| `MaxPingTime` | uint32 | `30` | `AMBROSE_MAX_PING_TIME` | At startup, and live once 4.15's reload triggers call the database loader | Minutes an idle database connection waits before it pings the server to stay open |
| `Updates.EnableDatabases` | uint32 | `3` | `AMBROSE_UPDATES_ENABLE_DATABASES` | At startup; schema updates never run on a live reload, so the running binary keeps the schema it was built for | Bitmask of databases the updater brings current before their pools open: 1 login, 2 characters, 4 world; a missing key means 0, none |
| `Updates.AutoSetup` | bool | `1` | `AMBROSE_UPDATES_AUTO_SETUP` | At startup | Create a missing database with utf8mb4. An empty database always gets `data/sql/base/db_<name>` imported, and a failed import into a database created this way drops it again |
| `Updates.SourcePath` | string | empty | `AMBROSE_UPDATES_SOURCE_PATH` | At startup | The Project Ambrose folder that holds `data/sql`; empty uses the folder the server was built from, then `share/ambrose` next to an installed `bin` |
| `Account.UsernameMinLength` | uint32 | `3` | `AMBROSE_ACCOUNT_USERNAME_MIN_LENGTH` | At startup, and live once 4.15's reload triggers call `AccountMgr::LoadSettings` | Shortest username new accounts may use (1-32). Usernames are at most 32 ASCII letters, digits, `_`, `-` and `.`, unique regardless of case |
| `Account.PasswordMinLength` | uint32 | `4` | `AMBROSE_ACCOUNT_PASSWORD_MIN_LENGTH` | Like `Account.UsernameMinLength` | Fewest characters a new password may have (1-128). Passwords are UTF-8 without control characters, at most 128 bytes |
| `Account.VerifierKeys` | string | empty | `AMBROSE_ACCOUNT_VERIFIER_KEYS` | Like `Account.UsernameMinLength`; a list that does not parse keeps the old keys, and stops startup | AES-256 keys that encrypt stored password verifiers, written `id:hex` with ids 1-255 and 64 hex digits each, separated by commas. Keep every key that still seals a stored verifier. Prefer the environment variable, so keys stay out of files |
| `Account.VerifierActiveKey` | uint32 | `0` | `AMBROSE_ACCOUNT_VERIFIER_ACTIVE_KEY` | Like `Account.VerifierKeys`; applies to verifiers written after the change | The key id that seals new and changed verifiers; 0 stores them unencrypted, and is refused at startup when `Account.VerifierKeys` lists keys. Otherwise it must name a key in that list |
| `Account.AllowPlainVerifiers` | bool | `1` | `AMBROSE_ACCOUNT_ALLOW_PLAIN_VERIFIERS` | Like `Account.UsernameMinLength`; applies to the next login or account lookup | Whether accounts whose verifier is still unencrypted may be used while a verifier key is active. Keep it 1 until every account has logged in once and been sealed, then set it to 0 so a verifier written straight into the database cannot be used |
| `Login.Name` | string | `Ambrose` | `AMBROSE_LOGIN_NAME` | At startup, and live once 4.15's reload triggers call `LoginMgr::LoadSettings`; each character list uses the settings current when it is built | The login server name sent as MSG_STARTCHARACTERLIST LoginServer, trimmed, at most 64 bytes; a longer value is reported and `Ambrose` is used. An empty name is allowed, and the reference server's captures show the client accepting one |
| `Login.EnforceRevision` | bool | `0` | `AMBROSE_LOGIN_ENFORCE_REVISION` | At startup, and live once 4.15's reload triggers call `LoginMgr::LoadSettings`; each attempt uses the settings current when it starts | Refuse clients whose MSG_USER_AUTHEN_V3 Revision is not in `Login.AllowedRevision`, with Error=ErrorNoLock. Ignored, with a warning, while that list is empty |
| `Login.AllowedRevision` | string | empty | `AMBROSE_LOGIN_ALLOWED_REVISION` | At startup, and live once 4.15's reload triggers call `LoginMgr::LoadSettings`; each attempt uses the settings current when it starts | Client revisions accepted while `Login.EnforceRevision = 1`, separated by commas, such as `r806919.Wizard_1_610` |
| `Login.MaxAuthAttempts` | uint32 | `5` | `AMBROSE_LOGIN_MAX_AUTH_ATTEMPTS` | At startup, and live once 4.15's reload triggers call `LoginMgr::LoadSettings`; each attempt uses the settings current when it starts | Guesses from one address, an IPv6 client counted by its /64 network, before the address is locked out, and failures of any kind before a session is closed (0-1000). Only a malformed or oversized Rec1, a wrong session id, an unknown account or a wrong password counts as a guess, and attempts still being checked count against the limit; 0 never locks out or closes |
| `Login.LockoutSeconds` | uint32 | `900` | `AMBROSE_LOGIN_LOCKOUT_SECONDS` | At startup, and live once 4.15's reload triggers call `LoginMgr::LoadSettings`; each attempt uses the settings current when it starts | How long a locked-out address is refused, and how long a failure is remembered (1-2592000) |
| `Login.DuplicateLoginPolicy` | uint32 | `1` | `AMBROSE_LOGIN_DUPLICATE_LOGIN_POLICY` | At startup, and live once 4.15's reload triggers call `LoginMgr::LoadSettings`; each attempt uses the settings current when it starts | What a login to an account another login server session holds does: 0 refuses it with Error=AuthenFailed and a message, 1 admits it and kicks the earlier session with MSG_FORCE_DISCONNECT |
| `Login.SessionKeyLifetime` | uint32 | `108000` | `AMBROSE_LOGIN_SESSION_KEY_LIFETIME` | At startup, and live once 4.15's reload triggers call `LoginMgr::LoadSettings`; each attempt uses the settings current when it starts | Seconds the session key a successful login issues stays valid; `account_session` stores its SHA-256 with the expiry (60-2592000) |
| `Login.AfkTimeout` | uint32 | `360` | `AMBROSE_LOGIN_AFK_TIMEOUT` | At startup, and live once 4.15's reload triggers call `LoginMgr::LoadSettings`; the next idle check uses it | Seconds a client that has not chosen a character may send no message before it is sent MSG_DISCONNECT_LOGIN_AFK and closed (0-86400); 0 never drops idle clients. Keepalives do not count as activity, and the check stops once a character is selected |
| `Login.AfkWarning` | int32 | `1` | `AMBROSE_LOGIN_AFK_WARNING` | At startup, and live once 4.15's reload triggers call `LoginMgr::LoadSettings`; the next idle check uses it | The Warning byte MSG_DISCONNECT_LOGIN_AFK carries (-128-127). The reference server sends 1; what the client does with other values is unverified |
| `Login.ShutdownGrace` | uint32 | `5` | `AMBROSE_LOGIN_SHUTDOWN_GRACE` | At shutdown | Longest a stopping login server waits, after closing its listener and sending MSG_LOGINSERVERSHUTDOWN to every client, for the notices to be written before it closes every connection (0-60 seconds); it stops waiting as soon as they are, and 0 sends no notice. A second signal does not shorten the wait |
| `Network.Threads` | uint32 | `1` | `AMBROSE_NETWORK_THREADS` | Live; new threads start at once, and removed threads stop taking sockets and exit when their last connection closes | Network threads that read and write sockets (1-256) |
| `Network.MaxFrameSize` | uint64 | `4194304` | `AMBROSE_NETWORK_MAX_FRAME_SIZE` | Next connection | Largest frame in bytes a client may send, checked before the frame is buffered (17 to 1 GiB) |
| `Network.MaxDmlMessages` | uint32 | `1024` | `AMBROSE_NETWORK_MAX_DML_MESSAGES` | Next connection | Most DML messages one frame may chain (at least 1) |
| `Network.MaxSendQueueBytes` | uint64 | `16777216` | `AMBROSE_NETWORK_MAX_SEND_QUEUE_BYTES` | Next connection | Most bytes a connection may have waiting to be sent (1 MiB to 1 GiB). A frame that would pass the limit is not queued and the connection is closed, so a client that stops reading cannot grow server memory without bound |
| `Network.LongFrameLength` | string | `BodyOnly` | `AMBROSE_NETWORK_LONG_FRAME_LENGTH` | Next connection | What a long frame's 32-bit length counts: `BodyOnly` or `HeaderAndBody`, until doc/CAPTURE.md settles it |
| `Network.OutKBuff` | int32 | `-1` | `AMBROSE_NETWORK_OUT_K_BUFF` | Next connection | Socket send buffer in bytes; -1 keeps the operating system default |
| `Network.TcpNoDelay` | bool | `1` | `AMBROSE_NETWORK_TCP_NO_DELAY` | Next connection | Disable Nagle's algorithm so small frames go out at once |
| `Network.SessionAcceptTimeout` | uint32 | `15` | `AMBROSE_NETWORK_SESSION_ACCEPT_TIMEOUT` | Next connection | Seconds a new connection has to answer SessionOffer with a matching SessionAccept before it is closed (1-3600) |
| `Network.KeepAliveInterval` | uint32 | `60` | `AMBROSE_NETWORK_KEEP_ALIVE_INTERVAL` | Next keepalive timer; a disabled timer checks again every second | Seconds between server keepalives to each accepted session; 0 sends none (0-3600) |
| `Network.KeepAliveTimeout` | uint32 | `15` | `AMBROSE_NETWORK_KEEP_ALIVE_TIMEOUT` | Next keepalive | Seconds after a server keepalive in which the client must send anything at all, or the session closes (1-3600) |
| `Network.MaxStrikes` | uint32 | `10` | `AMBROSE_NETWORK_MAX_STRIKES` | Next strike | Protocol violations a session may commit before it is closed (1-1000): a message only the server sends, a message from a service the app never accepts, an id the message definitions do not have, a body shorter than its definition, a dropped message beyond the dropped-message budget, or a MSG_PING beyond the ping budget. A message sent in the wrong session status, or one the server does not handle yet, is dropped and logged without a strike while the budget lasts |
| `Network.DroppedMessageBurst` | uint32 | `64` | `AMBROSE_NETWORK_DROPPED_MESSAGE_BURST` | Next connection | Dropped and refused messages a session may send in a burst while each is still logged (1-100000). Beyond the budget a dropped message is not logged and counts a strike instead, so a flood closes the session rather than filling the logs |
| `Network.DroppedMessagesPerSecond` | uint32 | `16` | `AMBROSE_NETWORK_DROPPED_MESSAGES_PER_SECOND` | Next connection | How fast the dropped-message budget refills (1-100000) |
| `Network.PingBurst` | uint32 | `16` | `AMBROSE_NETWORK_PING_BURST` | Next connection | MSG_PING messages a session may send in a burst that are each answered with MSG_PING_RSP (1-100000). A ping beyond the budget gets no answer and counts a strike, so a ping flood cannot make the server queue replies without bound |
| `Network.PingsPerSecond` | uint32 | `4` | `AMBROSE_NETWORK_PINGS_PER_SECOND` | Next connection | How fast the ping budget refills (1-100000) |
| `Log.Async.Enable` | bool | `0` | `AMBROSE_LOG_ASYNC_ENABLE` | Live | Write log lines on a dedicated thread; shutdown and exit drain every queued line |
| `Log.Async.QueueSize` | uint32 | `65536` | `AMBROSE_LOG_ASYNC_QUEUE_SIZE` | Live | Queued lines before the full-queue policy applies (1024-16777216) |
| `Log.Async.QueueFull` | uint8 | `0` | `AMBROSE_LOG_ASYNC_QUEUE_FULL` | Live | 0 waits for room, 1 drops the line and logs the drop count |
| `Log.Utc` | bool | `0` | `AMBROSE_LOG_UTC` | Live | Timestamps and file names in UTC instead of local time |
| `Log.PendingBuffer` | uint32 | `1000` | `AMBROSE_LOG_PENDING_BUFFER` | Live | Lines kept for an appender whose type registers later, such as DB |
| `Console.Colors` | uint8 | `1` | `AMBROSE_CONSOLE_COLORS` | Live, from the next line written | 0 never, 1 when stdout is a terminal, 2 always; `NO_COLOR` disables 1 |
