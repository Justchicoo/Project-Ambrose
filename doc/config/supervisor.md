# supervisor options

See doc/config/README.md for the file format, layers, environment variable names, and reload triggers, and doc/config/logging.md for the full logging grammar. The supervisor also reads every option the admin API takes, which doc/config/loginserver.md documents, with `Admin.Enable` on by default because serving the panel and answering power requests is what it is for, and with an empty `Admin.DashboardDir` serving the panel compiled into the supervisor rather than a `dashboard` folder beside it. It reads the same options a second time under the `Panel.` prefix for the panel's own listener, which is the front door people open in a browser: `Panel.Enable`, `Panel.BindIP`, `Panel.Port`, `Panel.Token`, `Panel.TokenFile`, `Panel.AllowPlainHttpRemote`, `Panel.CertificateFile`, `Panel.PrivateKeyFile`, `Panel.AuthFailureBurst`, `Panel.AuthFailuresPerSecond`, `Panel.MaxRequestBytes`, `Panel.Threads`, `Panel.DashboardDir`, `Panel.AllowedHosts`, `Panel.SessionIdleMinutes` and `Panel.SessionLifetimeHours` each mean for the panel what their `Admin.` twin means for an app, and every message about them names the `Panel.` option. `Panel.Enable` is `0` by default and `Panel.Port` is `12080`, which is clear of the login server's own `LoginServerPort` of 12000, since both run on one machine in the ordinary case. The panel listener binds this machine unless `Panel.CertificateFile` and `Panel.PrivateKeyFile` name a certificate and key, or `Panel.AllowPlainHttpRemote = 1` accepts that the token, sign-in passwords, two-factor codes and session cookies then cross the network unencrypted. `supervisor --panel-self-signed` writes a certificate that signs itself to those two paths and prints its fingerprint, for a panel on this machine. `supervisor --panel-link [username]` and `supervisor --panel-pair <username> --address <host[:port]>` ask the supervisor already running for a sign-in link through its admin API: they read `-c` and `--set` as the supervisor does, find the admin API by its `Admin.` options and read its token from `Admin.Token` or the token file without ever writing one, then print the link, or the pairing line, alone on standard output, with a note on who it signs in, from where and for how long, or the refusal, on standard error, so a program reads the one line it needs; nothing they see reaches a log, and they exit 0 with a link, 1 when none came back and 2 for a wrong command line. A local link opens the panel signed in once, from this machine only, within 60 seconds, as the operator named or the first owner; a pairing line is the panel's `#link` address with the token and the SHA-256 fingerprint of the certificate the panel listener serves, good once within 10 minutes. On a panel with no operator either one makes the owner, with a password nobody is told. The panel's operators are its own, kept in its store and separate from any game account: at each start while it has no operator it prints a one-time link, good for thirty minutes and only from the machine it runs on, that makes the owner with a name and password of their choosing, so no default password ever exists; a link printed before a restart still works after it until its own thirty minutes run out. `panel user list`, `panel user create <name>`, `panel user reset-password <name>`, `panel user disable <name>`, `panel user enable <name>`, `panel user link [name]` and `panel user pair <name> <host[:port]>` run on its console; create and reset-password take no password, printing a one-time link the operator sets their own from, so a password never reaches a console line, a log or an audit row. `panel user list` also says which operators have two-factor sign-in on, and `panel user reset-two-factor <name>` is the way back in for an operator who has lost both their authenticator and their recovery codes: it deletes their two-factor secret and every recovery code, ends every session they have and records it with the actor `console`, after which they sign in with their password alone until they turn it on again. A one-time password link sets the password and still asks for the second factor. `Panel.TrustedProxies` is a comma-separated list of addresses and CIDR ranges the panel believes a forwarded header from; with it empty, and for a peer not on it, the peer's own address is the client's and `X-Forwarded-For` is ignored, so nobody can name an address a throttle, an audit row or a sign-in record would believe. `Panel.RateLimitBurst` (default 120) and `Panel.RateLimitPerSecond` (default 2) size the cost-weighted limit held against the signed-in caller and against the address: each route says what answering it costs, a route that says nothing is never held back, and a request over the limit is answered 429 with `Retry-After` and recorded once per caller and minute in the audit tables.

The Applies column says when a changed value takes effect after a configuration reload or a live edit. The supervisor reads the options below when it starts watching, so the panel's config page marks them restart-required with that reason; milestone 17.28 moves launch settings into the panel's own store, where they apply at an app's next start instead.

| `Panel.StoreFile` | string | empty | `AMBROSE_PANEL_STORE_FILE` | At startup | The SQLite file the panel keeps its sessions, audit rows and later its users in, so it works before any game database is configured. Empty uses `panel/panel.sqlite3` in the Ambrose data folder, beside the supervisor's saved state, and a relative path is resolved against the working directory. It is opened when the supervisor starts watching and brought up to date by the dated files in `data/sql/panel` |
| `Panel.KeyringFile` | string | empty | `AMBROSE_PANEL_KEYRING_FILE` | At startup | The panel's keyring: the keys that seal every secret the panel must use again, such as two-factor secrets, and that make the keyed hashes recovery codes are found by. Empty uses `keyring` in the Ambrose data folder, beside `panel/` rather than inside it, so a copy of the store never carries the keys that open it, and a relative path is resolved against the working directory. A missing keyring is made with one key when the panel starts; one that is there but cannot be read stops the panel with an error naming the file and is left exactly as it was, because a new keyring would leave every secret the old one sealed unreadable. On Windows the file is wrapped with the data protection API for the account the supervisor runs as, and only that account, SYSTEM and Administrators may read it, so a keyring made while the supervisor ran as one account does not open under another: moving from a desktop run to a service under a different account needs that account to have made its own. Elsewhere it is mode 0600 and the folder holding it is narrowed to 0700 when it is wider, with a line in the log. Keep it with the store in every backup of the machine, and never in a copy of the store you hand anyone |

Each name is 1 to 32 letters, digits, dashes or underscores, names its own `App.<name>.*` options, and is the name the panel and the routes use. | `Backups.Dir` | string | empty | `AMBROSE_BACKUPS_DIR` | Live, on a configuration reload, which rebuilds the file roots | The folder backups are kept in, and the one the Files page shows as its backups root. ## Live settings and file roots

The supervisor keeps live settings of its own, listed in [settings.md](settings.md) with the apps that read them: `Files.MinFreeBytes`, `Files.MinFreePercent`, `Files.ReadMaxBytes` and `Files.ListMaxEntries`. With `Panel.Enable = 1` a change made on the settings page, the admin API or the `settings` console command is kept in the panel store's `settings` table with its `setting_audit` row and survives a restart; with the panel off they resolve from this file alone and a live change is refused. The file roots the Files page reaches are built from this file too, from `LogsDir`, `Backups.Dir`, each `App.<name>.Config` and the config that file names, and are rebuilt whenever the configuration is reloaded or the `file_roots` reload target runs.

## How a stop is asked for

A stop, a restart or the console's `stop` command tries, in order: the app's admin API (`POST /api/shutdown` with the countdown), a `shutdown` line on the app's input, which only an app this supervisor started still has, and an interrupt to the app's process group, which is Ctrl+Break on Windows and SIGTERM elsewhere. `kill` skips all of that and ends the process tree at once. The output says which way was taken and why.

## Console commands

`apps` lists every app with its state, process id and crash count. `start <app>`, `stop <app> [seconds]`, `restart <app> [seconds]` and `kill <app>` do what the panel's power buttons do. `shutdown` stops the supervisor itself and leaves the apps running; the next supervisor takes them back.

`panel user list`, `panel user create <name>`, `panel user reset-password <name>`, `panel user reset-two-factor <name>`, `panel user disable <name>` and `panel user enable <name>` manage the panel's operators while its store is open. `panel user reset-two-factor` is the console's answer to an operator locked out by a lost authenticator: it needs the machine, not the panel, so it works when no operator can sign in. `panel user link [name]` prints a local link that opens the panel signed in as that operator, or the first owner, once, from this machine only, within 60 seconds, and says who it signs in; `panel user pair <name> <host[:port]>` prints the one line a desktop program on another machine pairs with, the address, the SHA-256 fingerprint of the certificate the panel serves and a token good once within 10 minutes, and names the fingerprint again. On a panel with no operator both make the owner. `panel user create`, `panel user reset-password`, `panel user link` and `panel user pair` hand out a way to sign in, so they run only here, on the supervisor's own console: through the command route of the admin API or the panel they are answered refused with that reason, whatever level the caller holds.
